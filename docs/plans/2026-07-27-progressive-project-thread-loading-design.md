# 项目线程渐进加载设计

## 目标

单机视图刷新会话列表时，先展示项目目录，再并发加载各目录最近的线程。每个项目请求独立完成、独立更新，避免等待最慢项目后才一次性渲染全部结果。

## 范围

- 只调整单机视图的项目分组加载体验。
- “全部机器”视图继续使用现有“置顶 / 最近”结构。
- 项目首页仍只请求最近 5 条线程。
- 不引入线程内容缓存，线程数据仍直接来自 app-server。

## 数据流

1. 刷新开始时保留现有目录和线程。
2. 请求 `/api/projects`。
3. 目录返回后立即更新项目列表。
4. 同时并发发送每个目录的 `thread/list` 请求。
5. 每个项目请求返回后，立即替换该项目的首页线程。
6. 所有项目请求结束后，结束该机器的列表 loading 状态。

首次加载时，已经返回但尚未取得线程的项目显示 2 至 3 行局部骨架。刷新已有数据时继续显示旧线程，不在项目内显示刷新提示；机器名称前的状态标识在仍有首页项目请求时显示 loading。

## 状态模型

全局保留现有线程列表状态，并增加项目级首页加载状态：

- `idle`：尚未开始加载。
- `loading`：项目首页线程正在加载。
- `ready`：项目首页线程已成功返回。
- `error`：首次加载失败且没有可展示的旧线程。

机器级 loading 由当前首页项目请求的未完成数量推导。单个项目成功或失败都会减少未完成数量；全部请求结束后恢复 online。

## 更新规则

- 项目首次成功：写入该项目最近 5 条线程。
- 项目静默刷新成功：替换该项目最近 5 条线程。
- 首次加载失败：显示“加载失败，点击重试”。
- 静默刷新失败：继续显示旧线程，不清空数据。
- 项目重试：只重试对应目录，并让机器进入 loading。
- 快速重复刷新：复用当前在途刷新，避免重复请求。
- 新一轮刷新、客户端切换或重连后，旧 generation 的迟到响应不得覆盖新状态。
- 首页最近 5 条刷新不得覆盖已经通过“展开显示”加载的完整项目结果。

## 组件职责

### `thread-list-loader`

- 管理一轮项目首页请求的 generation 和在途去重。
- 在项目请求开始、成功、失败和整轮结束时分别回调。
- 不再等到 `Promise.all` 全部完成后才提交一次聚合结果。

### `BackendWorkspace`

- `/api/projects` 返回后立即保存目录。
- 按项目合并线程结果和加载状态。
- 将项目加载状态及重试命令暴露给顶层列表。
- 保留已有线程用于静默刷新。

### `ThreadListPage`

- 单机视图始终按已返回目录渲染项目分组，包括暂时没有线程的目录。
- 没有旧数据且处于 loading 时显示局部骨架。
- 初次加载失败时显示项目级重试按钮。
- 已有数据刷新时不显示项目刷新状态。
- “全部机器”视图保持现状。

## 测试

按 TDD 顺序覆盖：

1. 目录返回后可在任一项目线程返回前显示全部目录。
2. 项目请求独立返回时只更新对应项目。
3. 一个项目失败不阻塞其他项目成功渲染。
4. 初次加载显示局部骨架，刷新已有数据不显示项目刷新提示。
5. 初次失败显示项目级重试，只重试该目录。
6. 机器 loading 持续到全部首页项目请求结束。
7. 旧 generation 的迟到响应被忽略。
8. 快速重复刷新复用当前在途请求。
9. 首页刷新不覆盖已加载的完整项目线程。
10. “全部机器”视图的置顶和最近分组保持不变。
